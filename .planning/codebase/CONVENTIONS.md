# Coding Conventions

**Analysis Date:** 2026-04-24

## Naming Patterns

**Files:**
- React components: `PascalCase.tsx` - e.g. `client/components/List/List.tsx`, `client/components/Breadcrumb/Breadcrumb.tsx`
- SCSS modules: `<ComponentName>.module.scss` alongside the component - e.g. `client/components/List/List.module.scss`
- Generated SCSS declarations: `<ComponentName>.module.scss.d.ts` (committed, generated by `css-modules-typescript-loader`)
- Component-level business-logic hooks: `use<ComponentName>.ts` - e.g. `client/components/List/useList.ts`
- Shared hooks: `use<Thing>.ts` under `client/hooks/` - e.g. `client/hooks/useBreadcrumb.ts`, `client/hooks/useMergedState.ts`
- TypeGraphQL resolvers: `<Entity>Resolver.ts` - e.g. `server/graphql/resolvers/customer/CustomerResolver.ts`, `server/graphql/resolvers/timesheet/TimesheetResolver.ts`
- Mongo services: lowercase `<entity>.ts` under `server/services/mongo/` - e.g. `server/services/mongo/customer.ts`, `server/services/mongo/time_entry.ts`, `server/services/mongo/api_token.ts` (snake_case is used where a concept has two words)
- GraphQL query/mutation files: camelCase `.gql` - e.g. `client/graphql-queries/user/userDatabaseUpdateStatus.gql`, `client/graphql-mutations/customer/updateCustomers.gql`
- Utilities: camelCase `.ts` - e.g. `client/utils/fuzzyMap.ts`, `server/utils/generateId.ts`
- Test files: co-located `<source>.test.ts` (never `.spec.ts`) - e.g. `server/utils/generateId.test.ts`
- Barrel files: always `index.ts` / `index.tsx`
- Types: `types.ts` co-located with the component or resolver

**Components:**
- Exported React components are typed `ReusableComponent<TProps>` (alias over `StyledComponent<T>`) - see `client/components/types.ts`
- Components are named functions/const arrows with `displayName`, `className`, and `defaultProps` attached after declaration (see `client/components/Breadcrumb/Breadcrumb.tsx`, `client/components/List/List.tsx`)
- Props interfaces are prefixed with `I` and suffixed with `Props` - e.g. `IBreadcrumbComponentProps`, `IListProps`

**Hooks:**
- `use<Thing>` camelCase, returning an object (destructuring convention), not positional tuples for anything beyond 2 values
- Component-specific hooks live in the component folder (e.g. `useList.ts`)

**Resolvers (TypeGraphQL):**
- One class per entity, decorated with `@Service()` (TypeDI) and `@Resolver(EntityClass)`
- Injected services prefixed with underscore: `constructor(private readonly _customer: CustomerService)`
- Resolver methods named after the GraphQL field they serve (e.g. `customers()`, `createOrUpdateCustomer()`, `deleteCustomer()`)

**Mongo services:**
- Class name is `PascalCase + Service` - e.g. `CustomerService`, `TimeEntryService`
- Extend `MongoDocumentService<T>` and call `super(context, '<collection>', <ServiceName>.name)`
- Decorated `@Service({ global: false })` - one instance per request
- Inject `@Inject('CONTEXT') readonly context: RequestContext` plus any sibling services

**Variables:**
- camelCase for variables and function names
- UPPER_SNAKE_CASE for constants - e.g. `DEFAULT_MIN_WIDTH`, `MAX_COLUMN_WIDTH` in `client/components/List/hooks`
- Action creators (Redux Toolkit) UPPER_SNAKE_CASE - e.g. `SET_SORT`, `PROPS_UPDATED`

**Types:**
- Interfaces prefer `I`-prefix (`IListProps`, `IListColumn`, `IBreadcrumbItem`, `IAuthOptions`)
- AGENTS.md rule: prefer interfaces over type aliases; explicit return types for exported functions

## Import Organization

**Order (enforced by `prettier-plugin-organize-imports`):**
1. `reflect-metadata` (required once at the top of TypeGraphQL entry files - see resolver tests/servers)
2. External packages (`react`, `lodash`, `@fluentui/...`, `type-graphql`, `typedi`)
3. Path-aliased internal modules (`components`, `utils`, `hooks`, `AppContext`, ...)
4. Relative imports (`./`, `../`)

**Path Aliases (client only - `client/tsconfig.json > paths`):**
- `components`, `parts`, `pages`, `hooks`, `utils`, `logging`, `theme`, `i18n`
- `graphql-queries`, `graphql-mutations`
- `AppContext` -> `./app/context`
- `DateUtils` -> `../shared/utils/date`
- `security` -> `../shared/config/security`
- `package` -> `../package.json`

**Server:** no path aliases - relative imports only.

## Component Pattern (Client)

Every component in `client/components/<ComponentName>/` follows this layout (see `client/AGENTS.md`):

```
ComponentName/
├── ComponentName.tsx         # Functional component, returns JSX
├── ComponentName.module.scss # SCSS module imported as `styles`
├── ComponentName.module.scss.d.ts  # generated
├── index.ts                  # re-exports only (`export { X as Y } from './X'` + `export * from './types'`)
├── types.ts                  # Props interface(s) and exported types
└── useComponentName.ts       # business-logic hook (optional, for complex components)
```

Concrete example (`client/components/Breadcrumb/Breadcrumb.tsx`):

```tsx
import { Breadcrumb } from '@fluentui/react-breadcrumb-preview'
import { ReusableComponent } from 'components/types'
import React from 'react'
import { renderBreadcrumbItem } from './renderBreadcrumbItem'
import { IBreadcrumbComponentProps } from './types'
import styles from './Breadcrumb.module.scss'
import { mergeClasses } from '@fluentui/react-components'

export const BreadcrumbComponent: ReusableComponent<
  IBreadcrumbComponentProps
> = (props) => {
  return (
    <div className={mergeClasses(BreadcrumbComponent.className, props.className)}>
      <Breadcrumb size='large'>
        {props.items.map((item) => renderBreadcrumbItem(item, props.items))}
      </Breadcrumb>
    </div>
  )
}

BreadcrumbComponent.displayName = 'Breadcrumb'
BreadcrumbComponent.className = styles.breadcrumb
BreadcrumbComponent.defaultProps = { items: [] }
```

Key points:
- Arrow-function component typed `ReusableComponent<TProps>` (adds `displayName`, `className`, `defaultProps` statics)
- `displayName`, `className`, and `defaultProps` are always attached after the function declaration
- `index.ts` re-exports the component with a clean public name (e.g. `export { BreadcrumbComponent as Breadcrumb }`)
- SCSS module imported as `styles`, class names composed via `mergeClasses` from `@fluentui/react-components`
- Complex components extract stateful logic into `use<ComponentName>.ts` (see `client/components/List/useList.ts`)

## Styling

- SCSS modules (`.module.scss`) - always imported as `styles`, BEM-like class naming inside the file
- Prefer Fluent UI v9 primitives (`@fluentui/react-components`, `@fluentui-contrib/*`) over custom HTML
- Compose class names with `mergeClasses(...)` from Fluent
- Use Fluent design tokens (`tokens.colorPaletteRedForeground1`, etc.) instead of hardcoded colors

## TypeGraphQL Resolver Pattern (Server)

`server/graphql/resolvers/<entity>/<Entity>Resolver.ts`. Canonical example (`server/graphql/resolvers/customer/CustomerResolver.ts`):

```ts
import 'reflect-metadata'
import { Arg, Authorized, Mutation, Query, Resolver } from 'type-graphql'
import { Service } from 'typedi'
import { PermissionScope } from '../../../../shared/config/security'
import { CustomerService } from '../../../services/mongo'
import { IAuthOptions } from '../../authChecker'
import { BaseResult } from '../types'
import { Customer, CustomerInput } from './types'

@Service()
@Resolver(Customer)
export class CustomerResolver {
  constructor(private readonly _customer: CustomerService) {}

  @Authorized()
  @Query(() => [Customer], { description: 'Get customers' })
  customers() {
    return this._customer.getCustomers()
  }

  @Authorized<IAuthOptions>({ scope: PermissionScope.MANAGE_CUSTOMERS })
  @Mutation(() => BaseResult, { description: 'Create or update customer' })
  async createOrUpdateCustomer(
    @Arg('customer', () => CustomerInput) customer: CustomerInput,
    @Arg('update', { nullable: true }) update: boolean
  ) {
    // ...
    return { success: true }
  }
}
```

Rules:
- `@Service()` (TypeDI) + `@Resolver(EntityClass)` on the class - order matters
- Every query/mutation carries a `@Authorized()` or `@Authorized<IAuthOptions>({ scope })` decorator (bare `@Authorized()` = any authenticated user, typed variant = specific permission)
- Descriptions go in the decorator options object (`description`)
- Injected services are prefixed `_` (enforced by convention, not a lint rule)
- Type resolver inputs with TypeGraphQL classes (`CustomerInput`, not raw interfaces) and use `@Arg('name', () => Type)`
- Folder contains `<Entity>Resolver.ts` + `types.ts` + `index.ts` barrel

## Mongo Service Pattern (Server)

`server/services/mongo/<entity>.ts`. Canonical example (`server/services/mongo/customer.ts`):

```ts
import { FilterQuery } from 'mongodb'
import { Inject, Service } from 'typedi'
import _ from 'underscore'
import { RequestContext } from '../../graphql/requestContext'
import { Customer } from '../../graphql/resolvers/types'
import { MongoDocumentService } from './document'
import { LabelService } from './label'

@Service({ global: false })
export class CustomerService extends MongoDocumentService<Customer> {
  constructor(
    @Inject('CONTEXT') readonly context: RequestContext,
    private readonly _labelSvc: LabelService
  ) {
    super(context, 'customers', CustomerService.name)
  }

  public async addCustomer(customer: Customer): Promise<void> {
    await this.cache.clear('getcustomers')
    // ...
  }

  public getCustomers(query?: FilterQuery<Customer>): Promise<Customer[]> {
    return this.cache.usingCache<Customer[]>(
      async () => { /* ... */ },
      { key: ['getcustomers', query], hash: 'sha256' }
    )
  }
}
```

Rules:
- `@Service({ global: false })` - scoped per request (multi-tenant safety)
- Extend `MongoDocumentService<T>` from `server/services/mongo/document.ts` (provides `this.cache`, `this.insert`, `this.update`, `this.find`, `this.collection`)
- Always invalidate cache (`this.cache.clear('<key>')`) before write operations
- Cache reads via `this.cache.usingCache(fn, { key, hash: 'sha256' })`
- Each service exported through `server/services/mongo/index.ts` barrel

## GraphQL Query/Mutation Pattern (Client)

- `.gql` files, one operation per file, under `client/graphql-queries/<entity>/` or `client/graphql-mutations/<entity>/`
- Operation name is PascalCase, filename is the camelCase operation name
- Query example (`client/graphql-queries/user/userDatabaseUpdateStatus.gql`):

```graphql
query UserDatabaseUpdateStatus {
  userDatabaseUpdateStatus {
    running
    startedAt
    progressPercent
  }
}
```

- Mutation example (`client/graphql-mutations/customer/updateCustomers.gql`):

```graphql
mutation UpdateCustomers($customers: [CustomerInput!]!) {
  updateCustomers(customers: $customers) {
    success
    successCount
    failureCount
    errors { customerKey message }
  }
}
```

Rules (from `client/AGENTS.md`):
- Fragments live under `client/graphql-client/fragments/`
- Apollo Client configured with `InMemoryCache` + `fetchPolicy: 'cache-and-network'`
- Consume via `useQuery` / `useMutation` inside components or hooks
- Fetch only the fields you need - no over-fetching
- `.gql` files are loaded via webpack `graphql-tag/loader` (see `webpack/` config)

## Error Handling

**Client (from `client/AGENTS.md`):**
- Top-level React Error Boundary lives in `client/parts/ErrorFallback/`
- User-facing errors surface via toast notifications (`client/components/Toast/`)
- `console.log` is disabled in production by webpack - never add debug logs to committed code

**Server (from `server/AGENTS.md`):**
- Structured logging via `debug('namespace')` from the `debug` module, NOT `console.log`
- Express error middleware is registered in `server/app.ts`
- GraphQL errors are formatted centrally - throw `GraphQLError` with `extensions.code` (see `authChecker` emitting `UNAUTHENTICATED` / `FORBIDDEN`):

```ts
throw new GraphQLError('Not allowed', { extensions: { code: 'FORBIDDEN' } })
```

- Resolvers return `{ success: boolean, error?: {...} }` shapes (see `CustomerResolver.deleteCustomer`) using `_.pick(error, ['name', 'message', 'code', 'statusCode'])` to sanitize

## Logging

**Framework:** `debug` module (server), console is a last resort (client, dev-only).

**Patterns:**
- Server: `const debug = require('debug')('did:<namespace>')` then `debug('message %o', data)`
- Client: no custom logger - lean on React Error Boundary + toast + structured error payloads from GraphQL

## Internationalization

- All user-facing strings go through `useTranslation` from `react-i18next`
- String tables at `client/i18n/en-GB.json`, `client/i18n/nb.json` (Norwegian Bokmal), `client/i18n/nn.json` (Norwegian Nynorsk)
- Registered in `client/i18n/index.ts`
- Keep terminology consistent across all three languages
- Interpolation uses i18next syntax: `"{{hours}}"`, and markdown/HTML links are allowed inside strings (see `timesheet.matchOutlookInfoText`)
- For new strings: add the key to all three JSON files in the same commit

## Accessibility

From `client/AGENTS.md`:
- All interactive elements need appropriate ARIA attributes (`aria-label`, `aria-colspan`, etc. - see `client/components/List/List.tsx` toggle-all button)
- Keyboard navigation must work throughout
- Use semantic HTML - `button` / `nav` / `a`, not `div`, for interactive elements
- WCAG contrast compliance required; use Fluent design tokens for colors
- Provide alt text for images and icons
- Manage focus explicitly in dynamic/modal content (Panels, Dialogs)

## Function Design

**Size:** keep functions focused; extract helpers rather than nest callbacks deeply.

**Parameters:** prefer a single options object for >2 params; destructure at the call boundary.

**Return Values:** explicit return types are required per `AGENTS.md`. Avoid `any` in public API surfaces.

## Module Design

**Exports:** named exports everywhere - the codebase avoids `export default`.

**Barrel Files:** every folder with multiple public symbols has an `index.ts` that re-exports. Example (`client/components/Breadcrumb/index.ts`):

```ts
export { BreadcrumbComponent as Breadcrumb } from './Breadcrumb'
export * from './types'
```

## Comments & JSDoc

- Exported functions, React components, TypeGraphQL resolvers, and Mongo services carry JSDoc
- TypeDoc-style `@category GraphQL Resolver` / `@category Injectable Container Service` tags used on server classes (see `CustomerResolver`, `CustomerService`)
- `eslint-plugin-tsdoc` is enabled but `tsdoc/syntax: 'off'` - style is not enforced strictly, but documentation is expected

## Dependency Injection

- `typedi` throughout the server
- `@Service()` on resolvers, `@Service({ global: false })` on per-request services
- Request context injected via `@Inject('CONTEXT')`
- Services are constructed by the container - never `new CustomerService(...)` in production code (tests do construct directly with `as any` mocks; see CONCERNS/TESTING)
